# 技术文档写作

## 文字表达

文档应简洁易懂，准确说明技术事实及其原因。简化表达时保留必要的条件和术语，避免刻意口语化。例如：

> 模型目录中有某个模型，但本机没有该 provider 的凭据，所以它会出现在模型列表里，但暂时不能使用。

这类表达可以直接使用，无需将“模型目录中有某个模型”改成“Pi 知道这个模型”，也无需补充“这个区别非常重要”等评价。

术语以行业通用名称或项目中的实际名称为准，不随意造词或缩写。正文中优先使用“知识库”“尚未实现的方法”等明确表述，避免直接使用含义不清的 `kb`、`stub`。引用代码名称时，应结合上下文说明其含义。

避免 AI 味较重的描述，例如反复使用“不是 X，而是 Y”，用“赋能”“闭环”等抽象词代替具体说明，或在段尾添加“这正是该设计的核心价值”之类的空泛总结。也不要为追求“说人话”而刻意使用“自己查”“换着名字叫”等口语。修改这类句子时，直接说明实际行为、原因和结果；没有补充信息的句子可以删除，不必换一种说法重复。

## 内容组织

文档需要有明确的主线，各章节之间应有连续的讲解顺序。架构说明通常可以从启动过程或一次请求展开，结合执行流程介绍相关模块，说明模块之间的调用关系和数据传递。

例如，介绍会话创建时，可以依次说明设置与扩展的加载、模型选择、会话创建和用户输入处理。相关函数随流程介绍，参数和其他详细信息另列参考章节。仅按类或函数逐个介绍职责，无法充分说明系统的整体工作过程。

上手指南按实际操作顺序组织，设计方案则从需要解决的问题开始。章节长度和表现形式由内容决定，不要求每节都有相同的结构。

## 图示

涉及流程、模块关系、调用顺序或状态变化时，尽量配合图示说明，可使用文字图或 Mermaid。简单流程用文字图即可，例如：

```text
加载设置和扩展 → 选择模型 → 创建会话 → 处理用户输入
```

存在多个分支时可用 Mermaid 流程图，多个对象之间的调用可用时序图。图放在对应的讲解附近，名称与正文一致，箭头注明必要的条件或传递内容。复杂流程可以拆成几张图，文字补充原因和细节，避免将全部信息挤进一张图。

## 示例说明

复杂流程、容易混淆的概念和特殊情况，应在相关段落中配合示例说明。例如，解释缓存更新顺序时：

> 请求 A 先发出，请求 B 后发出，但 B 先返回并更新了缓存。A 随后返回，如果直接写入，就会覆盖 B 的结果。

在这个例子之后，再介绍代码如何避免旧结果覆盖新结果。示例中的行为必须与实际实现一致，不能编造事故、数据或尚未实现的功能。代码片段省略了必要内容时，应注明省略部分。
